## 2. วิธีติดตั้งและรัน

```bash
cd server
npm install
cp .env.example .env      # แล้วแก้ค่าตามจริง (ดูหัวข้อ 3)
npm start                  # รันที่ http://localhost:3000
```

ข้อมูลเดิมของคุณ (จาก `data_seed/*.json`) จะถูกนำเข้า SQLite ให้อัตโนมัติในการรันครั้งแรกเท่านั้น
(เช็คจาก log: `[db] นำเข้าข้อมูลชุดเดิมจาก data_seed/*.json เข้า SQLite เรียบร้อย`)

ถ้าต้องการ "รีเซ็ตข้อมูลทั้งหมด" ให้ลบโฟลเดอร์ `data/` ทิ้งแล้วรันใหม่ (จะ import จาก `data_seed/` ให้อีกครั้ง — ถ้าไม่ต้องการข้อมูลชุดเดิมแล้ว ให้ลบ `data_seed/` ด้วย ระบบจะสร้างผู้ใช้เริ่มต้นให้แทนผ่าน `db/seed.js`)

### แก้ไข Frontend
ซอร์สโค้ด frontend อยู่ที่โฟลเดอร์ `web/` (แยกจาก `server/`) รันตอนพัฒนา:
```bash
cd web
npm install
npm run dev     # เปิดที่ http://localhost:5173 (เรียก API ไป backend พอร์ต 3000 อัตโนมัติผ่าน proxy)
```
ตอน build จริง (`npm run build`) ไฟล์จะถูกคอมไพล์ไปวางที่ `server/public/` ให้อัตโนมัติ — แค่รัน `npm start` ที่ฝั่ง server ก็เสิร์ฟเว็บที่ build แล้วได้เลย ไม่ต้องรัน 2 พอร์ตพร้อมกันตอนใช้งานจริง

## 2.1 สรุปเรื่อง "แยก frontend/backend" ที่หลายคนสงสัยตอน deploy

**คำถามที่พบบ่อย: ต้อง deploy 2 อย่างแยกกันไหม ต้องตั้ง NSSM 2 ตัวไหม?**

**ไม่ต้อง** — ตอนใช้งานจริง (production) มันคือ **โปรเซสเดียว พอร์ตเดียว** เหมือนระบบเดิม (vanilla JS) ทุกประการ:

- `web/` (React + Vite) มีไว้แค่ตอน**พัฒนา/แก้ไขหน้าตา** เท่านั้น เวลาแก้เสร็จให้รัน `npm run build`
  ข้างในโฟลเดอร์ `web/` ซึ่งจะคอมไพล์ไฟล์ HTML/CSS/JS ไปวางไว้ที่ `server/public/` ให้เอง
- `server/` (Node.js) เป็นตัวเดียวที่ต้องรันตลอดเวลาบนเครื่อง production — มันทำหน้าที่ทั้งเป็น API
  และเสิร์ฟไฟล์หน้าเว็บที่ build ไว้แล้วจาก `server/public/` ในตัวเดียวกัน (ดูฟังก์ชัน `serveStatic()`
  ใน `server/server.js`)
- ดังนั้น **NSSM (หรือ PM2) ต้องตั้งแค่ 1 service เท่านั้น** ให้รัน `node server.js` ในโฟลเดอร์ `server/`
  เหมือนระบบเดิมเป๊ะๆ — `web/` ไม่ต้องรันบน production เลย ไม่ต้องมี service ที่ 2

**ขั้นตอน deploy จริงบนเครื่อง Windows (NSSM):**

```powershell
# 1) เตรียมไฟล์ (ทำครั้งแรก หรือทุกครั้งที่แก้ไขหน้าตาเว็บ)
cd web
npm install
npm run build          REM จะไปวางไฟล์ที่ ..\server\public\ ให้เอง

# 2) ติดตั้ง dependencies ฝั่ง server (ครั้งแรกเท่านั้น หรือเมื่อมี dependency ใหม่)
cd ..\server
npm install
copy .env.example .env
notepad .env            REM ตั้งค่า NAS_BACKUP_PATH, อีเมล, ฯลฯ ตามจริง

# 3) ตั้ง NSSM ให้รัน server ตัวเดียว (ทำครั้งแรกครั้งเดียว)
nssm install SchoolDocSystem "C:\Program Files\nodejs\node.exe" "C:\path\to\school-docsystem-vite\server\server.js"
nssm set SchoolDocSystem AppDirectory "C:\path\to\school-docsystem-vite\server"
nssm set SchoolDocSystem AppRestartDelay 5000   REM ให้ restart อัตโนมัติถ้าโปรเซสตาย (สำคัญมาก เพราะระบบมีรีสตาร์ทตอนตี 3 ทุกคืน)
nssm start SchoolDocSystem
```

**เวลาจะอัพเดตหน้าตาเว็บทีหลัง** (เพิ่มฟีเจอร์ใหม่/แก้บั๊ก UI) ทำแค่ขั้นตอน 1 ซ้ำ (`npm run build` ใน `web/`)
แล้วสั่ง `nssm restart SchoolDocSystem` เพื่อให้ค่า cache เก่าเคลียร์ — **ไม่ต้องตั้ง service เพิ่ม ไม่ต้อง deploy `web/` แยก**

> ⚠️ **หมายเหตุสำคัญที่แก้ไขในรอบนี้**: ไฟล์ `web/vite.config.ts` เดิมตั้งค่า `outDir` ผิดพลาดไปชี้ที่
> `../final/server/public` (โฟลเดอร์ที่ไม่มีใครเสิร์ฟจริง) แทนที่จะเป็น `../server/public` ที่ถูกต้อง
> ทำให้ที่ผ่านมาต่อให้แก้โค้ด frontend แล้ว `npm run build` เว็บที่เห็นจริงก็ยังเป็นเวอร์ชันเก่าค้างอยู่เสมอ
> (นี่คือสาเหตุของความสับสนเรื่อง "build แล้วไม่เห็นการเปลี่ยนแปลง") ตอนนี้แก้ไขให้ถูกต้องแล้ว

## 3. ตัวแปรแวดล้อม (.env) ที่ควรตั้งค่า

### 3.1 หลักการทำงานของระบบสำรองข้อมูล (อ่านก่อนสับสน)

**"ลบของเก่า" ที่เห็นในอีเมล/log หมายถึงลบจาก "เครื่อง server" เท่านั้น ไม่เกี่ยวกับ NAS เลย:**

- `BACKUP_KEEP` (ค่าเริ่มต้น 60) คือจำนวน "ชุดสำรอง" ที่เก็บไว้บนดิสก์ของเครื่อง server เอง — นับตาม
  **จำนวนครั้งที่สั่งสำรอง** ไม่ใช่นับเป็นวัน ถ้ากดปุ่ม "สำรองตอนนี้" เองบ่อยๆ ในวันเดียว จะกินโควตานี้เร็วกว่า
  60 วันจริง (ปกติมีแค่รอบอัตโนมัติตอนตี 3 วันละ 1 ครั้ง จึงเท่ากับ 60 วันย้อนหลังโดยประมาณ)
- เมื่อครบจำนวนแล้ว ระบบจะ**ลบชุดเก่าสุดออกจากโฟลเดอร์ `server/backups/` บนเครื่องนี้เท่านั้น**
- **ฝั่ง NAS ไม่ถูกลบตามนี้เลย** — ทุกครั้งที่สำรองสำเร็จ ระบบจะซิงค์ชุดล่าสุดขึ้น NAS แยกต่างหาก (คนละ
  ขั้นตอนกับการลบของเก่าบนเครื่อง) และ NAS จะสะสมไปเรื่อยๆ จนกว่าจะลบเองด้วยมือ (ผ่านหน้า "สำรองข้อมูล"
  ปุ่ม "ลบถาวร" ซึ่งอนุญาตให้ลบได้เฉพาะชุดที่เก่ากว่า 1 ปีเท่านั้น กันลบผิดพลาด)
- **หน้าเว็บจะยังคงเห็นชุดที่ถูกลบจากเครื่องนี้แล้ว ถ้ายังอยู่บน NAS** — เพราะหน้า "ประวัติสำรองข้อมูลบน NAS"
  ดึงรายชื่อไฟล์จาก NAS โดยตรงเสมอ ไม่ได้พึ่งพารายชื่อจากเครื่อง server เลย พูดง่ายๆ คือ: ลบจากเครื่องแล้ว
  ข้อมูลไม่หายไปไหน ตราบใดที่ NAS ยังเชื่อมต่อได้และมีชุดนั้นอยู่ ยังเห็น/กู้คืนได้ตามปกติจากหน้าเว็บ
- **ดูว่าข้างในชุดสำรองมีไฟล์อะไรบ้าง**: กดไอคอนรูปตา (👁) ข้างชื่อชุดสำรอง (ทั้งฝั่งเครื่องนี้และฝั่ง NAS)
  จะเห็นจำนวนเอกสาร/ผู้ใช้งาน ณ ตอนสำรอง และรายชื่อไฟล์แนบทั้งหมด — ถ้าเป็นชุดที่อยู่บนเครื่องนี้ กดดูรูป/PDF
  ได้เลยในตัว (ไฟล์บน NAS เปิดตรงไม่ได้เพราะอยู่คนละดิสก์ เห็นได้แค่รายชื่อ+ขนาดไฟล์)



ดูรายละเอียด/คำอธิบายทุกตัวในไฟล์ `.env.example` สรุปที่สำคัญ:

- `NAS_BACKUP_PATH` — ที่อยู่ NAS (เช่น `\\192.168.3.12\school-docsystem-backups` หรือ drive ที่ map ไว้) **ถ้าไม่ตั้งค่านี้ ฟีเจอร์ NAS ทั้งหมดจะแสดงสถานะ "ยังไม่ได้ตั้งค่า" อย่างปลอดภัย ไม่ error**
- `SMTP_HOST/PORT/USER/PASS/FROM` — สำหรับอีเมลสรุปผล backup รายคืน ถ้าไม่ตั้งค่า ระบบจะข้ามการส่งอีเมล (ไม่ error) และบันทึกเหตุผลไว้ใน log
- `BACKUP_REPORT_EMAIL` — ตั้งไว้เป็น `your-email@example.ac.th` แล้วตามที่ระบุ
- `VAPID_PUBLIC_KEY / VAPID_PRIVATE_KEY` — สำหรับ PWA push notification สร้างด้วย `node scripts/generate-vapid-keys.js`
- `SSL_CERT_PATH / SSL_KEY_PATH` — ถ้าใส่ path ไฟล์ใบรับรองไว้และไฟล์มีอยู่จริง ระบบจะรันเป็น HTTPS ให้อัตโนมัติ (ถ้าคุณมีใบรับรองอยู่แล้วตามที่กล่าวถึง ให้ใส่ path ตรงนี้ได้เลย) **ถ้าใช้ reverse proxy (IIS/Nginx/Caddy) ทำ HTTPS ให้อยู่แล้ว ไม่ต้องตั้งค่านี้** — ปล่อยเป็น HTTP ธรรมดาได้ตามเดิม เพราะ Push Notification จะทำงานได้ตราบใดที่ "หน้าเว็บที่ผู้ใช้เปิด" เป็น HTTPS (ไม่ว่าจะจาก reverse proxy หรือจากตัวเว็บเองก็ได้)

## 4. Deploy เข้าเซิร์ฟเวอร์จริง (NSSM)

`npm run deploy` ยังคงเป็นคำสั่งเดิม (คัดลอกไฟล์ไปที่ `\\192.168.3.12\c$\MyDoc`) — ไม่ได้แก้ไข เพราะเป็น workflow เฉพาะของคุณอยู่แล้ว

**หลังคัดลอกไฟล์ไปเครื่อง server**: รัน `npm install` ที่เครื่อง server หนึ่งครั้ง (better-sqlite3 เป็น native module ต้อง build/ดาวน์โหลด binary ให้ตรงกับ Windows+สถาปัตยกรรมของเครื่องนั้น — จะไม่สามารถคัดลอก `node_modules` ข้ามเครื่องแบบตรงๆ ได้ปลอดภัย)

**สำคัญเรื่องรีสตาร์ทอัตโนมัติตอนตี 3**: ระบบจะ `process.exit(0)` เองหลังส่งอีเมลรายงานทุกคืน โดยคาดหวังให้ NSSM (หรือ PM2) ตั้งค่า auto-restart ไว้แล้ว — เช็คว่า service ที่สร้างด้วย NSSM มี "Exit action" เป็น "Restart" (ค่า default ของ NSSM เป็นแบบนี้อยู่แล้วปกติ) ถ้าไม่อยากให้รีสตาร์ทอัตโนมัติ ตั้ง `NIGHTLY_RESTART_ENABLED=false` ใน `.env`

### 4.1 ดู log/สาเหตุตอน server ล่ม (แทนการเด้งหน้าต่าง cmd แบบระบบเก่า)

**ทำไมเด้งหน้าต่าง cmd ขึ้นมาเองแบบเดิมไม่ได้**: NSSM รันโปรแกรมเป็น "Windows Service" ที่ทำงานเบื้องหลังโดยไม่มีหน้าต่างเลยตั้งแต่ต้น (เพื่อให้รันได้แม้ไม่มีใคร login เข้าเครื่อง) จึงไม่มีทางที่ตัวโปรแกรมจะ "เด้งหน้าต่าง" ขึ้นมาเองได้ — นี่เป็นข้อจำกัดของสถาปัตยกรรม Windows Service โดยตรง ไม่ใช่ข้อจำกัดของโค้ดนี้

**สิ่งที่ทำได้จริงและตั้งค่าให้แล้ว:**

1. **หน้า "สถานะระบบ/Log"** ในเมนูแอดมิน — ดู uptime, การใช้หน่วยความจำ, กิจกรรมล่าสุดแบบเรียลไทม์ได้ผ่านเว็บเลย ไม่ต้องเปิดเครื่อง server เลย (รีเฟรชอัตโนมัติทุก 5 วินาที) **ข้อจำกัด**: ถ้า server process หยุดทำงานไปเลย (ล่มจริง เปิดเว็บไม่ได้) หน้านี้จะใช้ไม่ได้ด้วยเช่นกัน เพราะมันก็คือหน้าเว็บที่ต้องพึ่ง server เดียวกัน

2. **ให้ NSSM เขียน log ลงไฟล์** (สำหรับกรณี server ล่มจนเปิดเว็บไม่ได้เลย) ตั้งค่าตอนสร้าง service:
   ```powershell
   nssm set SchoolDocSystem AppStdout "C:\path\to\school-docsystem-vite\server\nssm-stdout.log"
   nssm set SchoolDocSystem AppStderr "C:\path\to\school-docsystem-vite\server\nssm-stderr.log"
   nssm set SchoolDocSystem AppRotateFiles 1
   nssm set SchoolDocSystem AppRotateBytes 10485760
   ```
   หลังตั้งค่านี้ ทุก error ที่ Node.js พิมพ์ออกมา (เช่น uncaught exception ที่ทำให้ process ตาย) จะถูกเก็บไว้ในไฟล์ `nssm-stderr.log` ให้เปิดดูย้อนหลังได้เสมอ แม้ตอนนั้นเว็บจะเปิดไม่ได้แล้วก็ตาม — เข้าไปเปิดไฟล์นี้ด้วย Notepad ได้ตรงๆ

3. **ถ้าอยากได้ภาพที่ใกล้เคียง "หน้าต่าง cmd เด้งขึ้นมา" ที่สุด**: ใช้คำสั่งนี้ที่เครื่อง server (เปิด cmd ค้างไว้) เพื่อดู log สดๆ แบบ tail:
   ```powershell
   powershell -Command "Get-Content C:\path\to\server\nssm-stderr.log -Wait -Tail 20"
   ```
   จะเห็น error ใหม่ๆ ไหลเข้ามาเรื่อยๆ เหมือนเปิด console ทิ้งไว้จริง (ต้องเปิด powershell ค้างไว้เองครั้งหนึ่ง ไม่ใช่เด้งขึ้นมาอัตโนมัติ)

## 4.5 ฟิลด์ "แนบไฟล์เอกสาร" (fileContent) — ต้องติดตั้ง LibreOffice บนเซิร์ฟเวอร์

ใช้กับเอกสารที่รูปแบบไม่ตายตัวมากจนพิมพ์ในระบบไม่สะดวก (เช่น คำสั่งโรงเรียน) — ให้แนบไฟล์ Word/PDF จริงแทน
ระบบจะแปลง .docx เป็น PDF ให้อัตโนมัติที่เซิร์ฟเวอร์แล้วแสดงตัวอย่างฝังในหน้าเว็บเลย (ดูรายละเอียดเหตุผลการออกแบบ
ใน CHANGELOG.md หัวข้อ v2.5.0)

**ต้องติดตั้งก่อนใช้งานฟีเจอร์นี้ได้:**

1. **LibreOffice** — ดาวน์โหลด/ติดตั้งจาก https://www.libreoffice.org/ (เวอร์ชัน Windows ปกติ) เซิร์ฟเวอร์จะเรียก
   `soffice.exe --headless` เพื่อแปลงไฟล์ ถ้าไม่พบ ระบบจะเตือนตอนสตาร์ท (ดูใน log) และฟิลด์นี้จะแปลง PDF ให้ไม่ได้
   (ผู้ใช้ยังดาวน์โหลดไฟล์ต้นฉบับไปเปิดเองได้ปกติ ไม่กระทบฟีเจอร์อื่น)
2. **ฟอนต์ไทยราชการ** (เช่น TH Sarabun New) — ดูขั้นตอนละเอียดที่ `server/fonts/README.md` แล้วรัน
   `server/scripts/install-fonts.ps1` (Windows, รันแบบ Administrator) ถ้าข้ามขั้นตอนนี้ ไฟล์ยังแปลงได้ปกติ
   แต่หน้าตาอาจไม่ตรงกับต้นฉบับเป๊ะ (ใช้ฟอนต์สำรองแทน — จากการทดสอบยังอ่านออกครบ ไม่ถึงกับเพี้ยนจนอ่านไม่ได้
   แต่แนะนำให้ติดตั้งฟอนต์จริงเพื่อความแม่นยำสูงสุด)

ตั้งค่า path ของ `soffice` เองได้ด้วย env `SOFFICE_PATH` ถ้าติดตั้งไว้ตำแหน่งที่ไม่ใช่ค่าเริ่มต้น

### Troubleshooting: LibreOffice ค้างตอนรันเป็น Windows Service (NSSM)

**อาการ:** ทดสอบบนเครื่อง dev (รัน `node server.js` ตรงๆ จาก terminal) แปลงไฟล์ได้ปกติ แต่พอ deploy ขึ้น
UAT/production ที่รันผ่าน NSSM เป็น Windows Service แล้ว **ใช้งานไม่ได้เลย** — log ขึ้น
`spawnSync ... soffice.exe ETIMEDOUT` (ค้างจน timeout ทุกครั้ง)

**สาเหตุ:** LibreOffice มีส่วนที่เป็น GUI toolkit อยู่ข้างใน แม้เรียกด้วย `--headless` ก็ตาม เวลารันภายใต้
Windows Service (ทำงานใน Session 0 ที่ไม่มี desktop/ผู้ใช้ล็อกอินอยู่) มันจะพยายามเข้าถึง Window Station หรือ
โฟลเดอร์โปรไฟล์ผู้ใช้ที่ service account (มักเป็น Local System/Network Service) ไม่มีจริงหรือเข้าถึงไม่ได้
ทำให้ค้างรอไปเรื่อยๆ จนกว่าจะ timeout — เป็นปัญหาที่รู้จักกันดีของแอปตระกูล LibreOffice/OpenOffice เวลารันเป็น
service ไม่ใช่บั๊กเฉพาะของระบบนี้

**สิ่งที่ลองแล้วในโค้ด (v2.6.2) แต่ถอนออกแล้ว:** เคยลองตั้งค่า `HOME`/`USERPROFILE`/`TEMP`/`TMP` ให้ชี้ไปที่
โฟลเดอร์ที่ควบคุมเอง แต่กลับทำให้เคสที่เคยใช้ได้ปกติ (รันตรงจาก terminal) พังไปด้วย จึงถอนกลับเป็นวิธีเดิมแล้ว
(v2.6.3) — **สรุปคือปัญหานี้ต้องแก้ที่การตั้งค่า Windows Service โดยตรง ไม่ใช่แก้ที่โค้ด** โค้ดฝั่งนี้เหมือนกัน
ทุกเครื่อง (dev/UAT/production) อยู่แล้ว ความต่างของอาการมาจากวิธีที่ Windows รัน service (ไม่มี desktop
session) ต่างจากตอนรันจาก terminal ปกติ (มี desktop session) ล้วนๆ ลองตามลำดับนี้:

1. **เปิด "Allow service to interact with desktop"** — Services.msc → หา service ของระบบนี้ (ชื่อตามที่ตั้งไว้ตอน
   สร้างด้วย NSSM) → คลิกขวา Properties → แท็บ Log On → ติ๊ก "Allow service to interact with desktop" → รีสตาร์ท
   service (ใช้ได้เฉพาะตอน service รันด้วย Local System account)
2. **หรือเปลี่ยนมารันด้วย user account จริงที่มี desktop profile ปกติ** — แท็บ Log On → เลือก "This account"
   ใส่ user/password ของ user จริงในเครื่อง (ต้อง login เข้า user นั้นอย่างน้อย 1 ครั้งก่อน เพื่อให้ Windows สร้าง
   โปรไฟล์ผู้ใช้ให้เรียบร้อยก่อน)
3. **หรือใช้ Task Scheduler แทน NSSM** — สร้าง Scheduled Task ตั้ง trigger "At startup", action รัน
   `node server.js`, ติ๊ก "Run whether user is logged on or not" — Task Scheduler มักจัดการเรื่อง session ให้
   แอปประเภทนี้ได้ดีกว่า raw Windows Service ตรงๆ
4. ถ้าลองทุกข้อแล้วยังไม่หาย ให้ลองรัน `soffice.exe --headless --convert-to pdf test.docx` ตรงๆ จาก Command
   Prompt ของ user/account เดียวกับที่ service ใช้ (ไม่ใช่ user ที่ล็อกอินอยู่ปกติ) เพื่อแยกให้ชัดว่าปัญหาอยู่ที่
   LibreOffice เองหรือที่การตั้งค่า service

หมายเหตุ: ฟีเจอร์ "แนบไฟล์เอกสาร" ออกแบบให้ล้มเหลวอย่างปลอดภัยเสมอ — ถ้าแปลง PDF ไม่สำเร็จ ผู้ใช้ยังกด
"ใช้ไฟล์นี้ทั้งไฟล์แทน" เพื่อแนบไฟล์ต้นฉบับได้โดยไม่ต้องรอแก้ปัญหา LibreOffice ให้เสร็จก่อน (ผู้เกี่ยวข้องจะ
ดาวน์โหลดไปเปิดเองแทนการดูตัวอย่างในระบบ)

## 5. สิ่งที่ทำเสร็จสมบูรณ์แล้ว (ทดสอบผ่านจริง)

- ย้าย JSON → SQLite โดยคงลอจิกเดิมทั้งหมดไว้ (ทดสอบ end-to-end แล้ว: login, เอกสาร, ผู้ใช้, แผนก)
- workflow อนุมัติใหม่ 3 ขั้น (สร้าง → ตรวจกรอง → เกษียน) พร้อมตีกลับ/ส่งใหม่/ไม่อนุมัติ/ถังขยะ ครบทุกเส้นทาง
- สิทธิ์หัวหน้าแผนกเพิ่มคนเข้าแผนกตัวเอง
- นำเข้าผู้ใช้จาก Excel/CSV/TXT พร้อมหน้าตัวอย่างก่อนยืนยัน
- สถานะ NAS + รายการ backup รายเดือน + อีเมลรายงาน + รีสตาร์ทอัตโนมัติ
- Frontend Vite/React/TS/Tailwind ครบทุกหน้าหลัก เชื่อม API ทำงานได้จริง (build ผ่าน ไม่มี TypeScript error)
- เปิด/ปิดเมนูฟังก์ชันจากหน้าแอดมิน
- ธีมสว่าง/มืด/กำหนดเอง + สลับภาษาไทย/อังกฤษ/จีน
- ตัวจัดหน้ากระดาษเอกสาร (ลากวางตำแหน่งฟิลด์บน canvas)
- PWA: service worker + manifest + Web Push จริง (ยังไม่มี VAPID key ใส่ไว้ล่วงหน้า ต้องรันสคริปต์สร้างเอง)

## 6. สิ่งที่ยังไม่สมบูรณ์ / ต้องทำต่อ (ตามที่แจ้งไว้ตั้งแต่ต้นว่าจะบอกตรงๆ)

- **ทดสอบในเบราว์เซอร์จริงแบบคลิกทุกปุ่ม** — ทดสอบผ่าน API (curl) ครบทุกเส้นทางหลักแล้ว แต่ยังไม่ได้เปิดเบราว์เซอร์จริงไล่คลิกทุกหน้า แนะนำให้ทดสอบก่อนใช้งานจริงกับข้อมูลจริง
- **Responsive ทุกจุดแบบละเอียด** — ใช้ Tailwind responsive class มาตั้งแต่ต้น (sidebar พับเป็นเมนูมือถือ, grid ปรับตามหน้าจอ) แต่ยังไม่ได้ไล่เช็คทุกหน้าทุกขนาดจอแบบละเอียด
- **การแก้ไขฟอร์มเอกสารตอนถูกตีกลับ** — ตอนนี้ resubmit ส่งข้อมูลเดิมกลับเข้าคิวได้ แต่หน้า UI สำหรับแก้ไขฟิลด์ก่อนส่งใหม่ยังเป็นแบบพื้นฐาน (ยังไม่ได้ทำฟอร์มแก้ไขแบบเต็มเหมือนหน้าสร้างเอกสาร)
- **PWA Push จริงบนมือถือ** — โค้ดพร้อมและทดสอบว่า API ตอบถูกต้องแล้ว แต่ยังไม่ได้ทดสอบการรับ push จริงบนอุปกรณ์ (ต้องมี HTTPS จริงถึงจะทดสอบสมบูรณ์ — localhost ทดสอบได้บางส่วนเท่านั้น)
- **ระบบเก็บเอกสาร/ไฟล์แนบไว้ที่ NAS เป็นหลัก** ตามที่พูดถึง (ให้ตัวเว็บเก็บแค่ข้อมูลเบื้องต้น ย้ายไฟล์เต็มไป NAS อัตโนมัติ) — ส่วนนี้ยังเป็นแค่ "อ่านสถานะ + ดู backup บน NAS" ยังไม่ได้ทำสถาปัตยกรรม "NAS เป็น storage หลัก" แบบเต็มรูปแบบ เพราะเป็นการเปลี่ยนสถาปัตยกรรมที่ใหญ่และเสี่ยงกระทบของเดิม แนะนำให้เป็นเฟสถัดไปแยกต่างหาก
- **i18n ยังไม่ครบ 100%** — ผูก context และพจนานุกรมหลัก (เมนู/ปุ่ม/สถานะ) ไว้ครบ แต่บางข้อความในหน้า (เช่นข้อความแจ้งเตือน error จาก backend) ยังเป็นภาษาไทยเสมอ เพราะ backend ส่งข้อความสำเร็จรูปมา ถ้าต้องการแปล error message ด้วยต้องแก้ที่ backend ให้ส่ง error code แทนข้อความ แล้วแปลฝั่ง frontend
